== `client-endpoint-url` is required

`xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-client-endpoint-url[quarkus.cxf.client."client-name".client-endpoint-url]`
has no default value anymore.

Before {quarkus-cxf-project-name} 4.0.0, a client without `client-endpoint-url` was sending requests to
`\http://localhost:8080/\{sei}`,
where `\{sei}` is the fully qualified class name of the service endpoint interface in lower case.
That URL was hardly ever right and a forgotten or misspelled `client-endpoint-url`
resulted in connection errors or `404` responses that did not point at the actual cause.

Since {quarkus-cxf-project-name} 4.0.0, a client without `client-endpoint-url` fails when it is created
with a message like

[source]
----
Cannot create the client myCalculator for the service interface org.acme.CalculatorService, because quarkus.cxf.client.myCalculator.client-endpoint-url is not set
----

This is a breaking change:

* Set `client-endpoint-url` for all your clients.
* This also applies to clients having
  `xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-wsdl[quarkus.cxf.client."client-name".wsdl]` set.
  The address available in the `wsdl:port` element of the WSDL is not used instead of `client-endpoint-url`.
* This also applies to clients whose address is set via `jakarta.xml.ws.BindingProvider.ENDPOINT_ADDRESS_PROPERTY`
  before each request.
* A client injected via `@CXFClient` without a client name fails when it is created,
  unless there is a `quarkus.cxf.client."client-name"` configuration having `service-interface`
  set to the service endpoint interface of the client.
  Before {quarkus-cxf-project-name} 4.0.0, such a client was created with default settings
  and only a warning was logged.
* The undocumented `quarkus.cxf.internal.client.*` options were removed.

See also xref:user-guide/advanced-client-topics/client-endpoint-url-defaults.adoc[`client-endpoint-url` is required]
and https://github.com/quarkiverse/quarkus-cxf/issues/2457[#2457].

== Dummy logging extension no longer published

`io.quarkiverse.cxf:quarkus-cxf-rt-features-logging` was deprecated since {quarkus-cxf-project-name} 2.7.0,
when all its functionality including configuration properties moved to `io.quarkiverse.cxf:quarkus-cxf`.
To keep backwards compatibility, a dummy `io.quarkiverse.cxf:quarkus-cxf-rt-features-logging` artifact still existed up to {quarkus-cxf-project-name} 3.40.* doing nothing else, but outputting a warning.

Since {quarkus-cxf-project-name} 4.0.0, `io.quarkiverse.cxf:quarkus-cxf-rt-features-logging` is no longer published. You can simply remove the dependency from your projects, as all its functionality has moved to `io.quarkiverse.cxf:quarkus-cxf`

== New `quarkus.cxf.client."client-name".vertx.http-versions` option

The new option
`xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-vertx-http-versions[quarkus.cxf.client."client-name".vertx.http-versions]`
defines the HTTP protocol versions that a SOAP client using `VertxHttpClientHTTPConduit` is permitted to use.
In contrast to the existing
`xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-version[quarkus.cxf.client."client-name".version]`,
it allows requiring HTTP/2 without any fallback to HTTP/1.x and using HTTP/3.

Only the following values are supported:

* `1.0` - use HTTP/1.0 only
* `1.1` - use HTTP/1.1 only
* `2` - require HTTP/2 without any fallback to HTTP/1.x
* `2,1.1` - prefer HTTP/2 and permit a fallback to HTTP/1.1
* `3` - require HTTP/3 without any fallback (experimental)
* `3,2,1.1` - start with HTTP/2 or HTTP/1.1 and switch to HTTP/3 once the service has advertised it (experimental)

Any other value, including other combinations and other orders of the above versions,
causes an exception on client creation.
The set of supported values is intentionally small and it may get extended in the future.

`xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-version[quarkus.cxf.client."client-name".version]`
keeps working as before.
It has to be left at `auto` when `http-versions` is set.

== HTTP/3 support for SOAP clients (experimental)

SOAP clients using `VertxHttpClientHTTPConduit` can use HTTP/3,
when
`xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-vertx-http-versions[quarkus.cxf.client."client-name".vertx.http-versions]`
is set to `3` or `3,2,1.1`:

* `3` makes the client use HTTP/3 for every request, without any fallback.
* `3,2,1.1` makes the client contact the service over TCP first
  and switch to HTTP/3 only after the service has advertised it via `Alt-Svc`.
* The application has to depend on `io.quarkus:quarkus-http3`.
  That extension makes the HTTP server of the application serve HTTP/3 too,
  see <<http3-for-soap-services>> below.
  Add `quarkus.http3.enabled = false` to `application.properties`, unless you want that.
* HTTP/3 requires `https:` URLs and it cannot be used through a proxy.
  Clients combining `3` or `3,2,1.1` with a plain `http:` URL or with a proxy are rejected.

See the documentation of
`xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-vertx-http-versions[quarkus.cxf.client."client-name".vertx.http-versions]`
for more details and limitations.

=== New options for HTTP/3 connections

The connection pool size and the keep alive timeout of HTTP/3 connections are configured separately
from the same settings for HTTP/1.x and HTTP/2 connections:

* `xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-vertx-connection-pool-http3-max-size[quarkus.cxf.client."client-name".vertx.connection-pool.http3-max-size]`
  sets the maximum pool size for HTTP/3 connections.
  The default is `1`.
* `xref:reference/extensions/quarkus-cxf.adoc#quarkus-cxf_quarkus-cxf-client-client-name-vertx-http3-keep-alive-timeout[quarkus.cxf.client."client-name".vertx.http3-keep-alive-timeout]`
  sets the number of seconds after which inactive HTTP/3 connections are closed.
  The default is `60`.

The existing options `vertx.connection-pool.http1-max-size`, `vertx.connection-pool.http2-max-size`,
`vertx.keep-alive-timeout` (HTTP/1.x only) and `vertx.http2-keep-alive-timeout` have no effect on HTTP/3 connections.

[[http3-for-soap-services]]
== HTTP/3 for SOAP services (experimental)

SOAP services exposed by {quarkus-cxf-project-name} can be called over HTTP/3,
if the application depends on `io.quarkus:quarkus-http3`, a new extension in Quarkus 4.0,
and if TLS is configured for the Quarkus HTTP server.
There are no new {quarkus-cxf-project-name} options for that.
Both JVM and native mode are supported.

Some limitations exist in the underlying projects:

* `quarkus-http3` in Quarkus 4.0 advertises HTTP/3 only on HTTP/1.x responses.
  Clients negotiating HTTP/2 for their first request stay on HTTP/2
  (https://github.com/quarkiverse/quarkus-cxf/issues/2446[#2446]).
* A request exceeding `quarkus.http.limits.max-body-size` or a stalled request body
  makes the server close the whole HTTP/3 connection, thus possibly aborting other requests sent through it
  (https://github.com/quarkiverse/quarkus-cxf/issues/2461[#2461]).
* With `quarkus-micrometer`, a `NullPointerException` is logged for requests terminated before completion
  (https://github.com/quarkiverse/quarkus-cxf/issues/2463[#2463]).
* `HttpServletRequest.getLocalAddr()` returns the wildcard address for requests received over HTTP/3,
  if the server listens on all network interfaces
  (https://github.com/quarkiverse/quarkus-cxf/issues/2464[#2464]).

See xref:user-guide/advanced-service-topics/http3.adoc[HTTP/3 for SOAP services] for more details.
